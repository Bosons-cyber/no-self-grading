# 工作区「agent 友好度」审计清单

**评估目标**：把一个工作区从「约定藏在人脑 / 历史对话里」改造成「**可机读、可校验、无歧义的显式事实**」。

**为什么它同时影响效果与成本**（这是本技能的核心论点）：

1. **token 效率**：新会话 / 新 agent 每次都要重新探查结构 —— 那是纯粹的重复开销。显式结构 = 一次读懂。
2. **LLM 效果**：文档里的约定互相矛盾时，模型读到的是**矛盾事实**，行为随机化、结论不可复现。
   把「权威事实源」显式化，等于给模型一个不可被污染的判断锚。
3. **协作正确性（人也是 LLM）**：多 agent 并行，或**多人团队项目（本质就是多 LLM 协作）**，
   如果没有明确的写权限边界，就会互相覆盖，而且**无法归因**。

> 判断标准统一为一句：**「一个没有历史上下文的新 agent，能否只靠仓库里的事实，正确、无歧义地开始干活？」**

> 📌 **本清单与平台无关。** 下文出现的文件名（`AGENTS.md` / `.cursor/rules` / `.codebuddy/` 等）
> 都只是**例子**：概念 → 各平台实际落点的对应关系见 `platform-mapping.md`。
> 判断某个维度时，先问「这个**概念**在目标平台叫什么」，不要拿某个平台的文件名当尺子。

## 评分表（10 维度 × 0-2 分，满分 20）

| 分档 | 含义 |
|---|---|
| 0 | 缺失 —— 新 agent 必然踩坑或猜测 |
| 1 | 部分 —— 存在但不完整 / 与事实不符 / 无强制 |
| 2 | 达标 —— 显式、一致、可校验、有维护机制 |

| # | 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|---|
| 1 | 入口机制 | 无任何入口文档 | 有 README 但不指向状态/规范 | 有强制加载的入口（规则文件）+ 入口文档指向「状态 + 规范」 |
| 2 | 单一事实源 | 同一事实多处副本且不一致 | 宣称共享但有内联复制 | 每类事实只有一个权威位置，且有「禁止复制」的明文约定 |
| 3 | 分工与写权限 | 无边界 | 定义了目录语义但没写权限 | 每目录标注职责 + 谁可写 + 冲突规避方式 |
| 4 | 状态与交接 | 无状态文件 | 只有全局状态，且人人可改 | 全局状态 + **每方向自己的状态文件**（只该方向写） |
| 5 | 引用一致性 | 无检查、迁移后大量失效 | 靠人眼抽查 | 有可回归的自检脚本，且 CI/hook 或流程中强制跑 |
| 6 | 版本控制 | 无 git | 有 git 但敏感物/大件未隔离 | git + 明确 `.gitignore`（凭据 / 外来源码 / 归档） |
| 7 | 记忆持久化 | 无 | 有目录但入口未引用 | 记忆文件被入口文档引用，跨会话自动读取 |
| 8 | 敏感数据卫生 | 凭据散落且可能入库 | 有凭据但未隔离 | 凭据不在工作区内，或被明确排除且不引用 |
| 9 | 规范自洽性 | 规范之间互相矛盾 | 有矛盾但没人踩 | 单一规范文档 + 与铁律一致 + 无悬空约定 |
| 10 | 判定独立性 | agent 能改测试 / 闸门配置 / 自检脚本，**且能自己合并** | 判据文件只靠文字规则「禁止改」 | 判据文件受 CODEOWNERS + 分支保护，**只有用户能合并**；每道闸门有独立来源的红样本 |

**判读**：≥17 分可交付；13-16 分「能用但会踩坑」；<13 分先修 P0。
**一票否决**：第 10 维为 0 分时，总分再高也**不可交付** —— 被判定的一方握着判定权，其余 9 维的「达标」都不可信。

## 各维度：查什么、怎么查

### 1. 入口机制
- **查**：是否存在**始终生效的规则 / 指令文件**？（落点按平台不同 —— Cursor / CodeBuddy 用
  `.mdc` + `alwaysApply`；Claude Code 用 `CLAUDE.md`；Copilot 用 `.github/instructions/`；
  跨工具通用的是 `AGENTS.md`。详见 `platform-mapping.md`。）
  根入口文档是否存在且**指向**状态与规范文档？子目录入口文档是否与根一致（不冲突）？
- **信号**：三层入口（规则 + 根导航 + 工作区导航）内容一致 = 达标。
- **坑**：这类文件只在**会话开始**加载 —— 改完要新开会话才生效，必须在文件里写清（否则会被误判为改动无效）。
- **断言**：本维度**不假设任何单一平台**；候选覆盖多平台，任一存在即算「有」。

### 2. 单一事实源
- **查**：同一份内容是否在多处出现？（用 `audit-workspace.py` 的「重复内容嫌疑」章节）
  特别是：人格/prompt 转录、规则副本、基线副本、模板。
- **信号**：`a/x.md` 与 `b/x.md` 内容哈希相同 → 强嫌疑。
- **修复**：收归一个目录，其他位置改为「引用 / 导入」，并在规范里写明「禁止各自复制」。
- **注意**：**用程序按行搬移 + 差异校验**，不要手抄（手抄必然引入偏差）。
- **查**：目录里有没有「**AI 生成**」的资料（并行 agent / 外部模型调研的产物）？
  它们**必须与人工核实的材料可区分** —— 否则会被下游当**事实源**引用。做法：**单列这一类** +
  头部强制标 `来源（哪个模型）+ 置信度（默认 \`未核实\`）` + 把「**引用前回源核对**」写成前置条件。
  详见 `traps.md` **D6**。

### 3. 分工与写权限
- **查**：有没有一张表写清「目录 → 职责 → 谁能写 → 备注」？只读/可追加/可新增是否区分？
- **信号**：出现「各 agent 可新增」与「只读」同时描述同一目录 → 矛盾（典型踩坑）。
- **坑**：权限定义若无强制手段（如目录所有权、CODEOWNERS）就只是君子协定 —— 至少要在规范里写清冲突规避规则。

### 4. 状态与交接
- **查**：除全局状态外，**每个方向/子项目是否有自己的状态文件**？字段是否包含：状态、上次更新、
  已完成、**未做及原因**、接手提示、上次的任务 ID？
- **查（上游索引是否同步）**：方向自己的状态文件更新之后，**上游索引**（方向索引 / 全局状态表里对应的那一行）
  是否跟着更新了？**「方向的状态已更新、上游索引没跟」是最常见的一种漂移** ——
  实践中两天内就出现过 **3 次**（方向收口、推进到下一步、方向改名各一次），每次都是索引落后一步。
- **信号**：`audit-workspace.py` 的「交接缺口」章节。
- **铁律**：**状态文件只由该方向写。** 全局单一状态文件 + 多 agent 写 = 并发覆盖。
- **修复（漂移）**：**状态文件是权威、索引是快照** ⇒ 每轮收尾**核对一次上游索引**；发现落后，
  以状态文件为准**回填索引**，而不是反过来改状态文件去迁就索引（否则就是「拿过期的快照否认真实进展」）。

### 5. 引用一致性
- **查**：跑 `scripts/verify-refs.py`。
- **信号**：`ERROR > 0` 即硬伤（文档指的路不存在 = 照做必失败）。
- **修复**：
  - 真失效 → 改引用；
  - 历史值（迁移映射表、模型原文引用）→ 加 `refs:skip-start/end` 豁免，**不要删历史**；
  - 生成物里的路径 → **修生成器**，不要只修产物（否则下次生成又坏）。

### 6. 版本控制与可回滚
- **查**：`git rev-parse --is-inside-work-tree`；`.gitignore` 是否覆盖「大件 / 凭据 / 归档 / 生成物」？
- **信号**：无 git = 多 agent 互相覆盖后**无法归因、无法回滚**（最严重的第 1 优先级问题）。
- **坑**：先建版本控制，**再**动手改文档 —— 否则改坏了没有安全网。

### 7. 记忆持久化
- **查**：是否存在跨会话记忆？（落点按平台不同：`.codebuddy/memory/`、`.claude/`、项目内
  `MEMORY.md` / `memory/` 等。）**关键是入口文档是否引用它。**
- **信号**：目录存在但没有任何文档指向它 → 其他 agent 不会读也不会写 → 形同虚设。
- **通用做法**：把记忆放在**项目内**（而不是平台私有目录）并用相对路径引用，跨平台最稳。

### 8. 敏感数据卫生
- **查**：`audit-workspace.py` 的「敏感文件候选」；私钥 / `.env` / 凭据文件是否在工作区内？
- **修复**：优先**移出**；不能移出时至少 gitignore + 在规范里标注「禁止引用」。
- **坑**：只 gitignore 不移动 = 只保证「不入库」，备份 / 打包 / 共享时仍会带走。

### 9. 规范自洽性
- **查**：把「铁律」与「结构规范」逐条对照，找矛盾（例：铁律说只读，规范说可新增）。
- **修复**：**以铁律为准**改规范；若有「无处可放」的内容类型（如工作区自身治理记录），
  明确指定归属位置，否则这类内容会长期流浪。

### 10. 判定独立性
- **原则**：判定「对不对」的权力，不能握在被判定的一方手里。agent 管「怎么做」，用户管「做什么」和「做完没有」。
- **判据文件**（下称「裁判」）= 测试 / 契约测试、闸门配置（`.agent-ready.json` 的 skip / 豁免 / 扫描范围、`GATES.md`）、概念词表 `vocab.json`、
  自检脚本（`tools/` 或 `scripts/`）、CI workflow 文件、`CODEOWNERS` 自身。
- **查**（只读命令，agent 可自己跑）：
  - 有远端吗：`git remote -v`
  - 远端的几项（主分支受保护吗、合并需要审批吗、有没有必过检查、agent 有没有合并权）**按平台查，见 `references/remote-platforms.md`**。
    GitHub 例：`gh api repos/{owner}/{repo}/rules/branches/main`（规则集，有读权限就能查）和 `…/branches/main/protection`（经典保护，要管理员权限）
  - **查到 403 / 404 只说明这个账号看不到，不说明没保护**：记「没查」，先用规则集接口确认，还看不到就请用户用自己的账号查。
    只有拿到结果、且结果确实是没保护，才按没保护记分（本维最多 0 分）。「没查」不算通过，也不能当 0 分直接下结论
  - CODEOWNERS 盖住裁判了吗：读 `.github/CODEOWNERS`（或根目录 / `docs/` 下同名文件），确认测试目录、闸门配置、
    自检脚本、`.github/workflows/`、`CODEOWNERS` 本身都归用户
  - agent 的凭据有没有合并权：按平台查（GitHub 例：`gh api repos/{owner}/{repo}/collaborators/{agent-account}/permission`，
    应为 `read` / `triage` / `write`，**不能**是 `maintain` / `admin`；若用户本人账号兼作 agent 凭据，本维最多 1 分）
  - 每道闸门有红样本吗：对照 `GATES.md`，每行的「红样本」列指向存在的文件；**关掉这道闸门时红样本必须报红**
- **信号**：规则文件里写着「不准改测试」，但没有任何机制拦 → 1 分（君子协定）；agent 能自己合并 → 0 分。
- **坑**：规则不能自己执行自己（无限递归）。锚点必须落在 agent 够不着的地方：远端 + 分支保护 + CODEOWNERS。
  这些都只有用户能做 —— 列进 `USER-CHECKLIST.md`，不要假装 agent 已经做完。
- **坑**：「先怀疑检查器」这类条文等于给 agent 改裁判的许可。检查器确实错了，走 `proposals/`，由用户批。

## 交付物清单（做完应该有什么）

- [ ] 入口：规则文件 + 根导航 + 工作区导航（三者一致）
- [ ] `STATUS.md`（现状 / 待办 / 想法）+ `STRUCTURE.md`（唯一结构规范）
- [ ] 每个方向的 `STATE.md`（交接）
- [ ] 方向索引（有哪些方向 / 谁在写 / 状态）
- [ ] `.gitignore`（凭据 / 大件 / 归档 / 生成物）
- [ ] `scripts/verify-refs.py` + `.agent-ready.json`，且 `ERROR = 0`
- [ ] 记忆文件 + 入口引用
- [ ] 「新增物 → 必须更新的文档」对照表（防文档漂移）
- [ ] `GATES.md` 闸门登记表 + `proposals/`（卡住时的出口）
- [ ] `USER-CHECKLIST.md`：「只有你能做」的项全部带验证命令，且验证通过（第 10 维的前提）
