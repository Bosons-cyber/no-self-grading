## A. 引用一致性检查（脚本实现层）

### A1 正则 lookahead 会迫使回溯成「更短的匹配」
- **现象**：检查器报出 `docs/securit`、`src/main.p`、`registry.yam` 这类**末尾少一个字符**的引用。
- **根因**：用 `(?![...])` 做「后面不能跟通配符」的判定时，正则会**退而求其次**匹配一个更短的前缀
  来满足 lookahead（`docs/security/*.md` → `docs/securit`），而不是放弃整个候选。
- **正确做法**：用**后置校验** —— 先让正则做最长匹配取出整段，再检查 `line[m.end()]` 是否属于
  「通配 / 模板 / 区间」字符集。也可以改 `(?>...)` 原子组（Python 3.11+），但后置校验更可移植。

### A2 遍历时的路径基准不一致 → 整棵子树没被跳过
- **现象**：明明配置了跳过 `archive/`，输出里却出现 `archive/xxx.md`。
- **根因**：跳过规则按「仓库根相对」书写，但 `walk()` 产出的是「相对遍历起点」的路径；
  当遍历起点不是仓库根（如从 `<<子目录>>/` 开始）时前缀匹配全部失效。
- **正确做法**：遍历时始终把结果换算成**仓库根相对**路径，再拿去做前缀匹配；只此一种基准。

### A3 破折号区间被截成假路径
- **现象**：`samples/S01–S09`、`out/deploy/R/R1–R4` 被报成失效引用。
- **根因**：`–`（en dash）不是路径字符，正则在此断开，留下一个不完整但「看起来合法」的路径。
- **正确做法**：把 `–` `—` `~` 一并放进「后缀字符集」，与 `*` `{}` `<>` 同等对待。

### A4 裸文件名索引不全 → 大量误报
- **现象**：文档引用 `OrderMapping.java`，检查器报「找不到」，但文件确实存在（在外部只读源码里）。
- **根因**：文件名索引只统计了「被扫描的范围」，没统计「可被引用的范围」。
- **正确做法**：**扫描范围**要窄（只扫 agent 会照着做的文档），但**文件名索引**要宽（覆盖全仓库）。

### A5 自检永远红 → 被忽略
- **现象**：检查器长期报一堆「失效引用」，但其中一部分是**故意保留的历史值**（迁移映射表、
  模型原文引证、虚构示例路径）。人一旦发现它常年红，就会开始忽略它。
- **正确做法**：必须提供**豁免机制**，且要分层：
  - 区间豁免（`skip-start`/`skip-end`）—— 历史表格；
  - 单行豁免（`skip-line`）—— 「目标路径」这类尚不存在的路径；
  - 文件级豁免（`allow-legacy`）—— 全篇都是历史引用；
  - 内置白名单 —— 故意不存在的虚构路径。
  **目标：`ERROR` 恒为 0。** 红着不管的自检等于没有自检。

### A6 Windows 下 Python 默认用 GBK 打开文本 → 含非 GBK 字符就崩
- **现象**：脚本在别人机器上跑得好好的，到 Windows 上 `UnicodeDecodeError: 'gbk' codec can't decode ...`，
  或者打印带 emoji / 中文时 `UnicodeEncodeError: 'gbk' codec can't encode ...`。连官方校验脚本都会中招。
- **根因**：Windows 上 `open()` / `Path.read_text()` / `print` 的默认编码是**本地代码页（GBK）**，不是 UTF-8。
- **正确做法**（两条一起上）：
  1. **读**文件时显式 `encoding="utf-8", errors="replace"`；**写**文件时显式 `encoding="utf-8"`；
  2. 脚本开头对 stdout 做 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`；
  3. 跑别人的脚本时先设 `PYTHONUTF8=1`（让 `open()` 默认 UTF-8）与 `PYTHONIOENCODING=utf-8`。
- **附带教训**：这类「环境相关」问题必须在工具里防御，否则工具只在作者机器上能用。

### A7 自检从错误的目录跑 → 假绿（`ERROR 0`，其实几乎什么都没扫）
- **现象**：输出 `ERROR 0` 一片绿，实际只扫了 **1 个文件**；换一种跑法又会得到**大量假 ERROR**
  （上百个「失效引用」），把人引去**改本来没坏的文档**。
- **根因**：检查器的解析基准（`scan.dirs`、跳过前缀、文件名索引）全都相对**仓库根**。
  从一个不同的 cwd 启动时，它先找不到 `<root>/.agent-ready.json`，于是**静默退化**成「只扫当前目录」，
  照旧打印 `ERROR 0` —— **绿得毫无意义，且没有任何提示**。
- **正确做法**：
  1. 命令与文档**一律写成从仓库根跑**（例：`python <repo>/tools/verify-refs.py --root .`）；
  2. 让检查器**自己怀疑**：配置不存在、或命中文件数远小于预期时**报错退出**，而不是打印 `ERROR 0`；
  3. **见到「假绿」或「假 ERROR」先怀疑 cwd，别改文档** —— 假 ERROR 会诱导人去改正确的引用。
- **✅ 本技能自带的 `verify-refs.py` 已内置这道闸门**：根上没配置、且（上级目录里**有**配置，
  或扫到的文件数 < 5）⇒ **拒绝给结论，退出码 2**，并打印四条修法；确知没问题时用 `--allow-untrusted-range` 显式放行。
  每次运行都会打印一行 `覆盖:` **声明本次扫描范围**（绿色必须带范围）。
- **教训**：`ERROR 0` 只有在**扫描范围确实覆盖了仓库**时才可信。**绿色必须带范围声明。**

### A8 检查器看不见「摘要式引用」→ 改名后最容易漏的一层
- **现象**：改了一个路径 / 代号 / ID，引用检查 `ERROR 0` —— 但**结论型摘要**（记忆文件、状态摘要、
  索引里的一句话结论）还写着旧值。因为它们只写「`X` 更名为 `Y`」，**不带任何路径形状的文本**，
  检查器根本看不见。
- **根因**：文本级引用检查只能匹配**路径形状**的字符串；而摘要层的工作方式恰恰是
  **丢掉原文、只留结论** —— 这是它省 token 的原因，也正是它漏改的原因。
- **正确做法**：**改名 / 改路径 / 改代号后，除跑检查器外，必须单独 grep 一遍「摘要层」**
  （记忆文件、状态摘要、索引结论条）。两者覆盖的东西**不同，不能互相替代**。
- **教训（通用）**：**每种检查都有覆盖边界，边界必须写进文档。** 不写，它就会被当成「都检查过了」。

### A9 含非 ASCII 文件名的路径被截断 → 「豁免列表」也是会漂移的第二处事实
- **现象**：搬迁 / 改名一批文件后，自检**突然报出一堆「解析不到」**，而报出的路径看着**像被砍掉一半**
  （例：报了 `…/design/PROJ-RUNTIME` 与 `…/design/PROJ-`，而真实文件名是
  `PROJ-RUNTIME运行时任务-….md`、`PROJ-能力分层.md`）。
- **根因**：检查器的路径正则（`PATH_RE`）**字符类不含 CJK** ⇒ 在**第一个中文字符处就停**，只能匹配前半截；
  项目为免它常红，把这类路径写进了配置的 **`ignore_refs` 豁免列表** —— 而**豁免项是按「旧路径字符串」写的**
  ⇒ **路径一搬，豁免立刻失效** ⇒ 那些"本来被豁免"的报错**全冒出来**。
- **正确做法**：① 把「**含非 ASCII 文件名的路径**」当**独立风险**登记（别只在配置里默默豁免）；
  ② **任何搬迁 / 改名后，同步改写 `ignore_refs`（或等价豁免列表）** —— **它和引用一样要跟着路径走**；
  ③ 报错里出现**明显被截断的路径**时，先想到**字符类限制**，别去改文档。
  ⚠️ **通用形式**：每种检查器都有**字符类 / 覆盖范围**边界；**用豁免兜住边界时，"豁免"就是第二处事实**，它同样会漂移。

### A10 用「shell 内联脚本」批量替换 → 宿主 shell 静默吃掉模式字符（0 命中且不报错）
- **现象**：批量改路径时写了 `python -c "…text.replace(老, 新)…"`，**6 个替换对全部 0 命中，且一个错都不报**。
- **根因**：模式里含**反引号**（Markdown 行内代码）—— 在 PowerShell 里**反引号是转义字符**，
  内联脚本在**交给 Python 之前**就被改写掉了 ⇒ 匹配不到、原样返回。
  ⚠️ 最危险的是**它不报错**：你会以为"已经改完了"。
- **正确做法**：① **不要用 shell 内联脚本做批量替换** —— 把脚本**落成文件**再跑（`.py` 里写反引号 / 引号完全安全）；
  ② 或**逐处用编辑工具**改；③ 无论哪种，**让脚本打印「每个替换对命中几处」，0 命中一律当失败处理**
  （本次正是靠这行输出才发现 6 个静默失败）。

## B. 路径与生成物

### B1 绝对路径被烤进产物，仓库一改就全坏
- **现象**：33 个生成出来的文档里写着旧工作区绝对路径（`C:/…/<旧名>/…`），迁移后全部失效。
- **根因**：生成器用 `dest.as_posix()`（绝对）把路径写进产物文档。
- **正确做法**：产物里一律写**仓库根相对**路径；同时**修生成器**，不要只改产物（否则下次生成又坏）。

### B2 只修产物、不修生成器
- **现象**：手工改好了所有产物文件，下次重跑生成器，问题原样回来。
- **正确做法**：先定位「这条错误路径由谁写入」，改源头，再决定是否需要重生成。

### B3 生成物被纳入「引用检查」范围
- **现象**：检查器在生成目录里报大量引用问题，但那些路径由生成器保证，改了也没用。
- **正确做法**：把生成物目录放进跳过前缀；**但**要保留一条「生成器输出格式」的检查意识 ——
  见 B1/B2。

## C. 多 agent / 多 LLM 协作

### C1 全局单一状态文件 + 多 agent 写 = 并发覆盖
- **现象**：两个方向同时更新同一个状态文件，一方的更新消失。
- **根因**：状态是**共享可变资源**，但没有所有权。
- **正确做法**：**状态分层** ——
  - 全局只放「稳定的索引与规范」（变更频率低、需广播）；
  - **每个方向一份自己的状态文件**，且**只由该方向写**。
  规范里明确写「只由 X 写」，比事后协调有效得多。

### C2 「只读」与「可新增」同时描述同一个目录
- **现象**：入口铁律说某目录只读，结构规范说「各 agent 可新增」，agent 只能猜。
- **根因**：同一事实在两地维护，且没有唯一权威。
- **正确做法**：确立**优先级链**（铁律 > 结构规范 > 局部 README），并把冲突方改成一致；
  如果某类内容「无处可放」，**明确指定归属位置**，不要让它在规范之间流浪。

### C3 没有「方向占用」信息 → 两人同开一个方向
- **现象**：两个 agent 各自新建同名目录并行开工，产出互不兼容。
- **正确做法**：一个**方向索引**（有哪些方向 / 谁在写 / 状态）+ 每个方向的状态文件里带 `status` 字段；
  规范里写「开工前先查占用」。

### C4 规则文件只在会话开始加载
- **现象**：改完入口规则文件，当前会话里没生效。**正确做法**：在规则文件里注明「改完需新开会话」，
  并让入口文档的指引不要依赖「马上生效」的假设。

### C5 多 agent 共用一个仓库 → `git add -A` 把别人的在途产物一起提交
- **现象**：agent 按「改动即提交」的约定跑 `git add -A && git commit`，把**另一个会话尚未做完**的文件
  （半成品脚本、中间产物、临时分析文件）一起提交；双方都以为「我只提交了自己的改动」。
- **根因**：`git add -A` 的作用域是**整个工作树**，而「改动即提交」隐含了「只有我在写」这个假设 ——
  在「一个仓库 / 多个 agent 并行」下假设不成立。且现场**毫无提示**：`git status` 看起来一切正常。
- **正确做法**：
  1. **禁止 `git add -A` / `git add .`**；提交前先 `git status`，**只显式 add 自己本轮改动的路径**。
  2. 提交前用 `git diff --cached --stat` 复核「暂存范围 == 自己声明的文件集」。
  3. **非自己产生的未跟踪 / 已修改文件：不 add、不改、不删**（需要时只留一句观察）。
  4. 别急着把它们加进 `.gitignore` 求「干净」——**先确认是不是项目惯例内的产物**
     （实例：某项目 `<team>/out/` 已跟踪 299 个文件，属**入库惯例**，未跟踪只表示「待提交」）。
  5. 这条要写进**入口规则**，不能只写规范文档 —— 它必须在会话开始就生效。

### C6 判断不出「另一个 agent 是否正在写」→ 拿中间态当结论
- **现象**：读同一批文件，几分钟内两次结果不同；按第一次读到的状态汇报，报出一堆**根本不存在**的问题。
  （实测：某一刻读到「文档 A 还是旧名、记忆 B 还是旧名」，**13 秒后**再看**两处都已改好** —— 对方当时正在写。）
- **根因**：`git status` 只说明「与上次提交不同」，**不说明新旧** —— 它分不清「别人刚写完、正在收尾」
  与「历史遗留」。而并行会话的写盘是**秒级**的。
- **正确做法**：
  1. **`mtime` 只是线索，不是判据**：它靠猜，近期被改过只说明「可能在途」，没改过也不说明「已收尾」；
  2. 你**没写过的**文件，只要对方没有明确交接，就视为**在途**：不 add / 不改 / 不删，**也不下结论**，
     需要时直接问对方或协调者；
  3. **静默时长只能说明「可能停了」，不能证明「已经交接」**：要接管别人的文件，须由对方或协调者明确交接
     （例如对方的 `STATE.md` 写明已收尾），不靠「等够几分钟」来判断。
- **附带教训**：**在中间态下结论 = 制造假问题。** 拿不准就先问对方或协调者，不要报一个不存在的缺陷。

### C7 「谁来提交」没有约定 → 成果长期停在磁盘上
- **现象**：子 agent 干完自己的方向就结束，产物一直是 `modified` / 未跟踪，没人提交。
  实测：一个方向的产物在盘上停了**几十分钟到两天**，而它同时已被别的会话当作「已存在」引用。
- **根因**：「谁来提交」**没有写成约定** —— 子 agent 以为协调者会收尾，协调者以为子 agent 会提交，
  于是出现「都以为别人会提交」的空档。
- **正确做法**：
  1. 写进约定：**谁写谁提交**；只有对方**没有提交权**时，才由协调者 / 主 agent 复核后代提交；
  2. **代提交前置**：确认对方已明确交接（见 **C6** 第 3 条）+ 敏感扫描（私钥 / `sk-` / 绝对路径）
     + 引用自检 `ERROR 0`；
  3. **提交信息里写明「这是代提交」以及含哪些来源** —— 否则后人看到「不属于某人的改动进了某人的提交」无法归因；
  4. 若一次提交里混进了别的东西（例：别人顺手做的一次文件压缩），**在日志里备案**，别让它无声无息。

## D. 事实源与文档

### D1 手抄转录必然引入偏差
- **现象**：把一段 prompt / 配置从 A 复制到 B，改掉一个词，之后两边慢慢分叉。
- **正确做法**：
  1. **收归单一事实源**，其他位置改为引用 / 导入；
  2. 搬移时用**程序按行取**，不要手抄；
  3. 搬完**做差异化校验**（加载新旧两份，断言逐字相等），并把校验结果写进提交说明。

### D2 声明了但不存在的事实源目录
- **现象**：规范里写着 `shared/persona/` 是「引擎人格事实源」，实际是空目录，人格被内联在某个脚本里。
- **危害**：比「没有这个目录」更糟 —— agent 会相信它存在，去读，读到空，然后自行发挥；而实际事实源在别处。
- **正确做法**：要么补齐并真正接线（其它地方改为引用），要么删掉声明。**不要留「假装存在」的目录。**

### D3 同名目录（仓库名 vs 子目录名）
- **现象**：仓库根叫 `X`，里面还有一个 `X/`；文档里写 `X/Y` 时无法判断从哪算起，git 仓库位置也易被误解。
- **正确做法**：在入口文档与结构规范顶部**显式警示**，写明「git 仓库 / 配置文件在父目录」，
  并统一规定「文档里的路径一律相对**仓库根**」。

### D4 敏感文件只 gitignore、不移动
- **现象**：私钥被加进 `.gitignore`，然后「问题已解决」。
- **事实**：那只保证**不入版本库**；备份、打包、共享目录时照样被带走。
- **正确做法**：优先**移出工作区**；无法移出时，gitignore + 在规范里标注「禁止引用」，
  并把它作为**显式残余风险**写进状态文档。

### D5 「缺失的授权方」—— 权限表写了但不落地
- **现象**：结构规范写「仅『事实源维护者』可写」，但没人知道谁是维护者、也没有机制标识。
- **正确做法**：把「谁可写」落到**可判定**的形式：目录所有权（CODEOWNERS）、
  或「每个方向自己的目录/状态文件」这种天然无争用的结构。

### D6 AI 生成的「调研资料」被当成事实源
- **现象**：让并行的 agent / 外部模型去做调研，产物写进知识库的「外部材料」目录，**看起来是一份正常报告**：
  有章节、有结论、甚至**自称「未知处标注公开信息不足、不编造」**。然后它被下游**当作依据引用**，
  一路进到对外文档里 —— 而**没有任何人回查过它**。
- **根因**：为**人类作者**设计的知识库约定（「外部材料 = 第三方原文」）**没有为「模型生成」这一类留位置**。
  于是模型产出被塞进同一个桶里，读起来没区别；而风险其实**多一层**：
  **来源不是「第三方机构」，而是「另一个模型」** —— 它可以**看起来合理却完全无法回查**
  （最极端的一份：全文 **0 链接、0 引用**，纯叙述型方法论，但照样会被当成"别人的做法"引用）。
- **正确做法（三条，缺一不可）**：
  1. **单列这一类**：在目录索引里把「**AI 生成**」和「第三方原文 / 人工核实材料」**分开标**，
     并写明处置规则；
  2. **强制标两件事**：`**来源：** <哪个模型 / 哪次并行调研>（**AI 生成**）` + `**置信度：** 未核实`，
     并在文档里**据实**统计它自带的出处（有几处链接 / 几处自标空白点）—— **不替它补来源**；
  3. **把「回源核对」写成引用前置条件**：⚠️ **产品名 / 价格 / 客户 / 业绩 /「尚无同类产品」这类断言，
     未经回查不得写进任何结论**（这类断言最像"事实"、也最容易是"听起来对"）。
- **推论（最实用的用法）**：这类材料当**「检索地图」**用最合适 —— 从它自带的出处清单出发**自己去回查**你要写进结论的那几条；
  **不要**直接当事实层。派生文档（"总对比/结论"）进一步**只能回溯到它的分册**，不能独立引用。
- **⚠️ 与「文献摘要 ≠ 实测结论」的区别（两条都要，不是一回事）**：
  那条防的是「**论文主张**被当结论」；这条防的是「**没有出处的模型文本**被当事实」。

## E. 调研与默认值

### E1 凭记忆断言「行业约定」，并据此定默认值
- **现象**：设计要交给别人用的技能 / 规范时，按自己的印象写出「业界标准是 X」，并把它设成默认值。
  事后一查：部分说法已过期、部分只是某一家平台的私有约定，还有一处「业界其实根本没有标准」被写成了惯例。
- **根因**：关于「常见约定」的记忆会过期，而且**无法被审阅** —— 读的人没有任何依据去质疑它。
  更糟的是：默认值一旦建立在错的约定上，后面所有使用它的人都会照着错。
- **正确做法**：
  1. **先取证，再定默认**。查官方文档 / 项目官方站；判断分量时看**传播面**（支持该约定的工具数、
     仓库数），而不是单个博客的推荐。
  2. **把来源、调查日期、置信度写进文档**（`官方 / 高可信二手 / 未核实`），让「过期」这件事**可见**。
     `未核实` 必须显式标出来，不能混在事实里。
  3. **默认值要能从证据推导出来**。例：默认「新建入口文档用 `AGENTS.md`」，依据是
     「官方站列 23 个工具支持 + 无必填字段 + 支持嵌套 + 由 Linux 基金会下的基金会托管」。
  4. **给一节「怎么重新取证」**，否则文档会静默过期。
  5. **如果业界没有标准，就明说这是空白点** —— 不要写成仿佛有惯例。
     把空白点讲清楚，恰恰是这类技能的价值所在。
- **落地**：先做**平台探测**（本技能 `audit-workspace.py` 的「平台画像」章节），
  **沿用目标仓库已有的约定**；只有什么都没探测到时，才套用证据最充分的默认值。
